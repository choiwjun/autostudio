## 1. 배경 및 문제 정의

- 사용자 목표: 네이버 블로그로 월 10만원 이상 수익 (애드포스트 + 쇼핑커넥트)
- 핵심 업무: "매일 쓸 주제(키워드)를 고르는 일" — 트렌드 파악, 경쟁 판단, 상업키워드 선별
- 문제: 크리에이터 어드바이저 트렌드탭은 내부 전용이라 API 없음. 검색량/애드포스트 데이터는 공식 API로 제공되지 않음
- 해결 방향: **프록시 신호**를 자동 수집·누적해 "글 쓸 가치가 있는 키워드"를 순위화하는 클라우드 기반 도구 (로컬 PC 불필요)
- **v2 추가 인식**: 경쟁도·신선도만으로는 "아무도 안 찾는 키워드"가 고득점하는 함정이 있음 → **데이터랩 상대 수요 확증을 v1에 포함**해 수요 신호 공백을 메움

### 검증된 공식 API 현황 (2026-08 확인)

| API | 용도 | 제한 |
|---|---|---|
| 검색 (blog) | 키워드별 글 수·상위글 발행일 | 25,000회/일 |
| 데이터랩(검색어트렌드) | 키워드 간 상대 수요 비교 (**앵커 방식**) | 1,000회/일, 요청당 그룹 5개 |
| 데이터랩(쇼핑인사이트, v4 편입) | 네이버쇼핑 검색 **클릭 추이** — 상업 수요 프록시 (**앵커 방식**) | 1,000회/일, 요청당 키워드 5개 |
| 검색 (shop) | ~~상품 수·가격·카테고리~~ — **2026-07-31 공식 종료** (v4) | - |
| 블로그 글 발행 API | **없음** (공식 목록에서 제외) | - |
| 애드포스트/쇼커 API | **없음** | - |

### 1차 목표 (v1)
키워드 발굴(자동완성 크롤링) + 경쟁도 분석(blog 검색) + 상업성 분석(shop 검색) + **수요 확증(데이터랩, 상위 후보만)** → 웹 대시보드 제공

## 2. 성공 지표 (v1 출시 후 4주 기준)

| 지표 | 목표 | 측정 방법 |
|---|---|---|
| 파이프라인 안정성 | 스냅샷 성공률 ≥ 99%, 무인 연속 운영 28일 | collection_runs / collection_log |
| 발굴 품질 | "유망"(기회 ≥ 70 · 상업성 ≥ 60 · 수요지수 ≥ 0.01) 키워드 주 10개 이상 | 대시보드 필터 |
| 실사용 | 발굴 키워드로 발행한 글 주 3건 이상, 4주 내 상위 노출 확인 5건 이상 | 수동 확인 (v1.5에서 발행 기록 기능으로 자동화) |
| 정원 관리 | 활성 키워드 수가 캡(1,000) 안에서 안정 (은퇴 ≈ 신규) | /status |

도구가 위 지표를 못 채우면 점수 공식·블랙리스트·앵커 키워드를 조정한다. 점수는 프록시이므로 **검증 가능한 가정**으로 취급한다.

## 3. 아키텍처 (클라우드 — 로컬 PC 불필요)

```
┌─────────────────────────────────────────────────┐
│  웹 대시보드 (HTML/JS 단일 페이지, Chart.js)      │
│  키워드 리스트/정렬/필터/페이징 · 상세 추이 그래프 │
│  시드 관리 · 키워드 제외 · 수동 수집 · 토큰 입력   │
└────────────────────┬────────────────────────────┘
                     │ REST API (쓰기는 Bearer 토큰)
┌────────────────────▼────────────────────────────┐
│  Vercel (Hobby 무료) — FastAPI (ASGI)            │
│  - 사전계산 점수 조회(단일 쿼리+페이징)           │
│  - 수동 수집(시간 예산 45초) - 시드/키워드 관리   │
└────────────────────┬────────────────────────────┘
┌────────────────────▼────────────────────────────┐
│  GitHub Actions (무료) — 매일 07:17 KST cron     │
│  collect.py: ① 자동완성 발굴 ② 정제 필터         │
│  ③ 스냅샷+점수 계산 ④ 데이터랩 수요 확증          │
│  ⑤ 저성과 은퇴 ⑥ 보존 기간 정리                  │
└────────────────────┬────────────────────────────┘
┌────────────────────▼────────────────────────────┐
│  Supabase Postgres (무료 500MB) — Supavisor 풀러 │
│  seed_keywords · keywords · daily_stats ·        │
│  top_results · collection_log · collection_runs  │
└─────────────────────────────────────────────────┘
```

**구성 원칙**
- 수집기(`collect.py`)는 GitHub Actions에서 독립 실행 (Vercel과 분리)
- 개발/테스트는 SQLite로 동일 코드 실행 (DB 레이어가 URL 스킴으로 백엔드 전환)
- 모든 외부 의존(자동완성 엔드포인트, API 키, 상한값, 토큰, 앵커)은 config/env 분리
- 무료 구성: Vercel Hobby + Supabase Free + GitHub Actions = 월 0원

**기준 시간대 원칙 (v2 신설)**
- 날짜 키(`day`), `first_seen`, 일일 상한 카운트, 신선도 컷오프, 로그 타임스탬프는 **전부 Asia/Seoul(KST) 기준**
- GitHub Actions/Vercel 런타임은 UTC이므로 `date.today()` 직접 사용 금지 — `config.today_kst()` / `config.now_kst_iso()`만 사용 (고정 오프셋 +09:00, KST는 DST 없음)
- 위반 시 증상: 22:00 UTC 실행분이 전날로 저장되고, 같은 KST 날의 수동 수집이 다른 날짜 키로 이중 기록되어 증감률이 오염됨

**DB 연결 방식 (v2 신설 — 배포 차단 요인)**
- Supabase **직결 주소(`db.<ref>.supabase.co:5432`)는 무료 티어에서 IPv6 전용** → GitHub Actions 러너·Vercel(Lambda)은 IPv6 아웃바운드 불가로 **연결 실패**
- 반드시 **Supavisor 풀러** 사용: GitHub Actions(장시간 배치) = Session 모드(5432), Vercel(서버리스) = Transaction 모드(6543). 두 저장소(GitHub Secrets / Vercel Env)의 `DATABASE_URL`은 서로 달라도 됨
- API 서버는 커넥션 사망(유휴 종료·풀러 재시작) 시 **1회 재연결 후 재시도**
- **수집 배치(collect.py)도 동일한 재연결 내장** (v3 정정): 단일 장시간 세션이므로 배치 중 풀러 재시작 시 DB 레이어가 1회 재연결 후 재시도

**클라우드 제약 (공식 문서 확인, 2026-08 / v2 정정 포함)**
- Vercel Python 런타임: FastAPI(ASGI) 지원 — `app` 변수 자동 감지. Hobby 함수 실행 한도 60초 → 수동 수집은 시간 예산 45초 적용
- Vercel Cron: Pro 전용($20/월) → 무료 플랜에서는 GitHub Actions cron 사용
- Supabase Free: 7일 무활동 시 프로젝트 일시정지. **재개는 대시보드에서 수동 복구** (v1의 "접속 시 자동 재개"는 오류였음 — 수집이 7일 실패하면 DB까지 잠기는 연쇄 장애 경로)
- GitHub Actions: **레포에 60일간 활동(커밋 등)이 없으면 스케줄 워크플로우 자동 비활성화** → 워크플로우에 keep-alive 스텝 내장(마지막 커밋 50일 경과 시 빈 커밋 푸시)
- GitHub Actions 무료 분량: private 레포 월 2,000분 → 아래 §10 용량 산정으로 관리

## 4. 컴포넌트 상세

### 4.1 자동완성 크롤러 (v2 개정)
- 입력: seed_keywords (분야별)
- 방식: 네이버 검색 자동완성 엔드포인트(비공식) 호출 → 연관 단어 BFS 2레벨 확장
- **기존 키워드 처리 (발굴 정체 수정)**: DB에 이미 있는 키워드는 ① 일일 신규 상한에 **계수하지 않고** ② BFS **경유지로는 사용**한다(더 깊은 신규 발굴 가능). v1은 재발견 키워드가 상한을 소진해 2일차부터 발굴이 정체되는 결함이 있었음
- **시드 분야 전파 (v3 신설)**: 시드에서 직접 파생된 1차 발굴 키워드는 시드의 category를 상속한다(2차 이상 BFS 경유 키워드는 미분류 — shop 데이터로 채움). 분야 필터가 신규 키워드에도 동작하기 위한 전제
- 상한 3종: 일일 신규 100개(`DAILY_NEW_KEYWORD_CAP`) · **활성 총량 캡 여유분**(§4.6) · 실행당 요청 수 300회(`AUTOCOMPLETE_MAX_REQUESTS`)
- **수동 실행 시간 예산 (v3 명시)**: 발굴도 예산에 포함된다. 예산이 남지 않으면 요청을 시작하지 않고 중단하며, 예산 초과 중단은 **차단(blocked)과 구분**해 기록한다(중단 사유 3종: 정상 완료 / blocked / budget)
- **재시도/차단 감지 (v1 스펙 약속의 실제 구현 요건)**: 요청당 지수 백오프 3회 재시도. 연속 5회 실패 **또는 성공 0회**면 크롤 중단(`blocked`) + collection_log에 `blocked` 기록. **차단은 스냅샷 성공 여부와 무관하게 exit 1**로 이어져 GitHub 실패 메일이 발송된다(§5) — 조용히 성공 처리 금지
- 응답 포맷은 비공식이므로 **방어적 파싱**(구/신 포맷 수용, 실패 시 빈 결과) + 구현 직후 실측 스모크 검증 단계 필수
- rate limit 준수 (요청 간 0.3초)

### 4.2 정제 필터 (v2 개정 — 2단 블랙리스트)
- 공백 정규화 후 중복 제거
- **부분문자열 블랙리스트**: 오탐 여지가 없는 문자열 (야동·바카라·카지노·슬롯·작업대출·마약·수면제·비아그라·시알리스·성인용품·랜덤채팅·유흥)
- **토큰 블랙리스트**: 단독 단어일 때만 차단 (성인·도박·대출·불법·사기·토토) → "성인병 예방", "전세대출 금리"는 통과 (v1은 부분문자열 일괄 매칭으로 정상 키워드 과차단)
- **포털 토큰**: 네이버·카카오·다음·구글·유튜브·인스타(그램)·페이스북·트위터가 토큰으로 포함되면 제거
- v1 블랙리스트에서 **홍삼 제거** (대표 수익 니치 — 차단 근거 없음)
- 필터링 사유를 collection_log에 저장 → **리젝 로그 주간 리뷰로 규칙을 다듬는 것을 운영 루틴에 포함**. 사유는 **반환 값에 포함**되어야 한다(부분문자열/토큰/포털/불용어 구분 — v3에서 "필터" 일괄 기록은 리뷰 입력이 되지 않음을 정정)

### 4.3 경쟁도 분석기 (키워드당 스냅샷)
- **blog 검색 2종**: 정확도순(sim) total + 상위 20개 발행일 → 상위글 신선도 / 최신순(date) total → 발행량 증감률
- ~~shop 검색~~ — **v4 제거**: 쇼핑 검색 API 종료(2026-07-31)로 상품 수·가격·카테고리 소실. 상업 신호는 §4.4의 쇼핑인사이트 배치로 대체
- 키워드당 호출량: blog 2 = **2회** (v3: 3회 → v4: 2회)
- 신선도 컷오프는 **호출 측이 KST 기준일을 명시적으로 전달** (내부에서 `date.today()` 호출 금지)

### 4.4 데이터랩 수요 확증 + 쇼핑 클릭 지수 (v4 개정)
- 목적: "저경쟁 = 저수요" 함정 차단. 기회점수 상위 **200개 후보만** 매일 상대 수요를 확인
- 방식: 요청당 앵커 키워드 1개 + 후보 4개 그룹(최근 30일, 일 단위) → `수요지수 = 후보 평균 ratio ÷ 앵커 평균 ratio` (요청 간 비교 가능하도록 앵커로 정규화)
- 앵커: 계절성 낮고 중간 규모인 키워드 (기본 `냉장고`, `DATALAB_ANCHOR`로 조정). 앵커 ratio 0이면 해당 배치 오류 처리
- 비용: 200후보 ÷ 4 = **50회/일** (한도 1,000회의 5%)
- 저장: `daily_stats.demand_idx` (미조회 키워드는 NULL → 대시보드에 "-")
- 활용: 수요지수 정렬·표시, 권장 로직에서 수요지수 < 0.01(앵커의 1% 미만)이면 "수요낮음" 처리
- 실패/쿼터 소진 시: 수요 단계만 중단하고 나머지 파이프라인은 정상 진행 (graceful degradation)
- **오류 정규화 (v3 신설)**: **네트워크 오류·타임아웃·잘못된 JSON까지 전부 DatalabError로 변환**한다. 변환 없이 원시 예외가 전파되면 `update_demand`의 except가 잡지 못해 스냅샷 성공 후 전체 실행이 failed로 처리되는 연쇄 장애가 생긴다(§6)
- **쇼핑 클릭 지수 (v4 신설)**: 쇼핑인사이트 `POST /v1/datalab/shopping/category/keywords`로 **키워드별 검색 클릭 추이**를 조회 → `shop_click_idx = 후보 평균 ratio ÷ 앵커 평균 ratio` (수요지수와 동일 앵커 정규화 패턴, 같은 배치 단계에서 함께 처리). `category`(쇼핑 분야 코드) 필수 — 기본 `50000000`(`SHOPPING_INSIGHT_CATEGORY`로 조정). 분야 미매칭(빈 응답) 키워드는 **NULL 유지**(0점 취급 금지 — 오탐 보호). 저장: `daily_stats.shop_click_idx`. 한도 1,000회/일 내 수요와 합산
- 비용 합산: 200후보 ÷ 4 = 50회(수요) + 50회(쇼핑 클릭) = **100회/일** (한도 1,000회의 10%)

### 4.5 점수 엔진 (v4 공식 개정)
```
기회 점수(0~100) = 40×상위글신선도 + 30×성장정규화 + 30×(1−경쟁도)
상업성 점수      = ~~60×min(상품수/500,1) + 40×min(평균가/30000,1)~~ — v4: 소스(shop API) 종료로 산출 중단(NULL 유지, 하위호환)
쇼핑 클릭 지수   = 쇼핑인사이트 앵커 대비 클릭 비율 (v4 — 상업 신호 프록시, §4.4)
수요지수          = 데이터랩 앵커 대비 비율 (별도 표시, 공식에 미합산)
```
- **상위글신선도**: 상위 20개 중 최근 7일 내 발행 비율 (KST 기준일)
- **성장정규화 (v2 정정)**: `clamp(일일증감률 / 0.05, 0, 1)` — 일 5% 증가에서 만점. v1의 [-100%, +100%] 정규화는 일일 증감률이 통상 0~2%라 30점 항이 사실상 상수(~15점)가 되는 변별력 결함이 있었음
- **경쟁도 (v2 정정)**: `min(1, log10(total) / log10(10,000))` — **1만 글에서 포화** (v1 계획은 10만으로 스펙과 불일치했음. 스펙 기준 1만으로 정합화)
- **점수는 수집 시점에 계산해 `daily_stats`에 저장** (growth/opportunity/commercial 컬럼). 조회 시 재계산 금지 — N+1 제거의 전제
- 증감률·기회점수는 **전일(day-1) 스냅샷**이 있어야 산출 (미달 시 NULL → "데이터 쌓는 중"). **공백(2일 이상)이 생기면 최근 과거 스냅샷으로 계산하지 않고 NULL** — 며칠치 증가율을 하루 증가율로 표시하는 오류 방지 (v3 정정)
- 원시값(raw)도 대시보드에 함께 노출 — 프록시 신호이므로 사용자가 직접 판단 가능하게 함

### 4.6 키워드 수명주기 (v2 신설 — 지속 가능성의 핵심)
v1은 무한 증식 구조였음(100개/일 누적 → 약 83일에 API 한도, 둘째 달에 Actions 분량 초과). v2는 **정원(garden) 모델**로 관리:
- **활성 총량 캡**: `ACTIVE_KEYWORD_CAP`(기본 1,000). 신규 발굴은 `캡 − 활성 수` 여유분 안에서만
- **자동 은퇴**: 발견 14일 경과 + 최근 7일 스냅샷이 존재하는데 기회 < 35 **그리고** (상업성 < 30 또는 쇼핑 클릭 < 0.5)이 전부인 키워드 → `active=0` + `retire` 로그. (최근 스냅샷이 아예 없는 키워드는 수집 실패일 수 있으므로 은퇴 대상에서 제외)
- **점수 NULL 보호 (v3 정정, v4 갱신)**: 최근 7일 창의 **스냅샷 중 하나라도 기회/상업성/쇼핑 클릭 점수가 NULL이면 은퇴하지 않는다**. v4에서 상업성은 항상 NULL(소스 종료)이므로 **은퇴 판정은 실제로 기회점수 + 쇼핑 클릭 지수로 동작**한다. 쇼핑 클릭 미조회(분야 미매칭 등) 키워드는 NULL로 보호 — COALESCE(점수, 0) 비교 금지
- **수동 제외**: 대시보드에서 키워드별 "제외" 버튼 (`PATCH /keywords/{id}`) — 필터를 통과한 쓰레기 키워드가 API 3회/일을 영구 소모하는 것을 차단
- **보존 정리 (v1의 "2차로 연기"를 철회)**: 매 수집 말미에 daily_stats 90일, top_results 30일(신선도 계산의 원본일 뿐이라 짧게), collection_log 180일 초과분 삭제

### 4.7 저장 (DB 레이어)
- **프로덕션**: Supabase Postgres (psycopg2, Supavisor 풀러 경유 — §3)
- **개발/테스트**: SQLite (`sqlite:///...` — `Database` 클래스가 스킴으로 백엔드 전환, 동일 인터페이스)
- SQLite 연결은 `check_same_thread=False` (FastAPI 동기 엔드포인트는 스레드풀에서 실행됨 — 누락 시 즉시 ProgrammingError)

| 테이블 | 내용 (v2 변경) |
|---|---|
| seed_keywords | 시드키워드 + 분야 |
| keywords | 키워드, first_seen(KST), 분야, active. **category는 비어있지 않은 값으로만 갱신**(v1은 무조건 UPDATE로 값을 지웠음) |
| daily_stats | 일자별 스냅샷 + **사전계산 점수 4종(growth/opportunity/commercial/demand_idx, NULL 허용)** + **shop_click_idx(쇼핑 클릭 지수, v4)** |
| top_results | 키워드별 상위 20개 발행일 (30일 보존) |
| collection_log | 키워드 단위 이벤트. run_at은 **ISO 타임스탬프(KST)** (v1은 날짜만이라 하루 2회 실행 순서 구분 불가) |
| collection_runs | **(신설)** 실행 단위 이력 + 실행 잠금 (started_at/finished_at/status/run_trigger/집계). **status: done(전량 성공) / partial(예산 종료·일부 오류·발굴 중단) / failed(예외·전량 실패·stale 회수)** (v3) |

**실행 잠금 (v3 재교체)**: v1의 `.lock` 파일은 GH Actions(매 실행 새 파일시스템)와 Vercel 사이에서 무력했고, v2의 SELECT→INSERT 순차 잠금은 경합 창이 있었다(동시 실행 2건이 모두 running 행을 만들 수 있음). v3는 **`collection_runs`에 `status='running'` 부분 유니크 인덱스를 걸고 조건부 INSERT로 원자 취득**한다 — 경합 시 하나만 성공. stale 기준은 **60분**(`RUN_LOCK_STALE_MINUTES`) — GH Actions `timeout-minutes: 60`과 정합(30분이면 30~60분 걸리는 장시간 실행이 다른 트리거에 회수됨). stale 회수는 running 행을 failed로 갱신한 뒤 취득을 재시도한다. GH Actions 쪽은 `concurrency` 그룹으로 1차 방어 유지. 같은 날짜에 이미 스냅샷된 키워드는 건너뛰어 재실행이 멱등이 되도록 함

### 4.8 API 서버 (FastAPI, v2 개정)
- `GET /keywords` — **단일 쿼리 조회**(키워드별 최신 스냅샷 조인). **스냅샷 없는 키워드도 반환(LEFT JOIN, v3)** — "데이터 쌓는 중" 상태 표시 전제. 정렬(기회/상업성/쇼핑클릭/수요/증감, NULL은 뒤로) + **정렬 방향(`sort_dir=desc|asc`, v3)** + **유망 프리셋(`preset=promising` → 기회≥70 & 쇼핑클릭≥0.5 & 수요지수≥0.01, v4)**, 필터(분야/상업성 최소/검색어/발견기간/비활성 포함) + **`click_min`(쇼핑 클릭 최소, v4)**, **페이징(page, page_size)**. v1의 키워드당 3쿼리(N+1)는 수백 개부터 대시보드를 마비시키므로 금지
- `GET /keywords/{id}` — 상세 + 일자별 추이 (사전계산 점수 포함 → **점수 추이 그래프** 가능, 404 처리)
- `PATCH /keywords/{id}` — active 토글 (인증 필요)
- `POST /collect` — body `{"trigger": "manual"}`(기본): 수동 수집, **시간 예산 45초가 발굴·개별 호출까지 전 구간 적용** (인증 필요) / body `{"trigger": "schedule"}`: **전체 파이프라인**(발굴→스냅샷→수요→은퇴→보존)을 Vercel 한도 내 예산(45초)으로 실행 — **cron-job.org 대체 스케줄러용** (v3)
- `GET/POST/DELETE /seeds` — 시드 관리 (쓰기는 인증 필요)
- `GET /status` — 활성 키워드/시드 수, 최근 실행(collection_runs), 마지막 성공 수집일(**status='done'만 성공으로 집계 — partial/failed 제외, v3**)
- `GET /categories` — 분야 목록 (**shop 카테고리 + 키워드·시드 분야 통합, v3**)
- 커넥션 오류 시 1회 재연결 재시도 (§3)

### 4.9 수동 수집 시나리오 (v3 재정의)
- 주 수집 경로는 스케줄러. 수동 버튼은 **보조**: 발굴은 생략하고 "오래된 스냅샷부터" 시간 예산(45초) 내에서 갱신, 초과분은 `partial=true`로 응답
- **예산은 전 구간 적용 (v3 정정)**: 발굴(첫 실행)·스냅샷 루프·**개별 API 호출 타임아웃까지** 예산에 포함된다. 키워드당 최악 blog 2 + shop 1 = 3회 호출이 잔여 예산을 넘지 않도록 호출 타임아웃을 잔여 예산 기준으로 축소한다. v2는 스냅샷 루프 사이에서만 체크해, 발굴 40요청 × 최악 30초(10초×3재시도) = 20분이나 키워드당 최악 30초 오버슛이 가능해 Vercel 60초 한도를 초과할 수 있었음
- **예외 — 첫 실행**: 활성 키워드가 0개면 축소 발굴(신규 30개·요청 40회)을 수행해 온보딩 흐름("시드 추가 → 지금 수집 실행")이 동작하게 함. 축소 발굴도 예산 내에서 중단될 수 있고, 예산 초과 중단은 차단과 구분 기록
- 대시보드 문구: "수동 수집은 일부 갱신용 — 전체 수집은 매일 아침 자동"

### 4.10 대시보드 (단일 HTML/JS, v2 개정)
- 테이블: 기회점수 | 상업성(★, ~~sh용~~ v4: 항상 NULL — 하위호환 표시) | **쇼핑클릭(v4)** | 수요지수 | 키워드 | 분야 | 총 글 수 | 증감률 | 데이터일수 | 권장 | **제외 버튼**
- 권장 로직 (v4): 수요지수 < 0.01 → "수요낮음" / 기회 ≥ 70 & **쇼핑클릭 ≥ 0.5** → "쇼커" / 기회 ≥ 60 → "애포" / 기회 ≤ 35 → "경쟁과열" / 그 외 "보류" (임계값은 초기값 — §2 지표로 조정)
- 페이징 UI(이전/다음), 검색은 서버 필터 + 300ms 디바운스
- 상세 모달: 기회점수·수요지수(좌축) + 총 글 수·상품 수(우축) 추이 그래프
- 토큰 입력(localStorage 저장, 쓰기 요청에 Bearer 헤더)
- 수집 버튼 응답 처리: partial("일부만 갱신됨"), locked("이미 실행 중"), 401("토큰 확인"), 타임아웃 안내
- **외부 유래 문자열(키워드 등)은 전부 이스케이프 후 삽입** — v1의 innerHTML 직접 삽입은 XSS 벡터
- 빈 상태 안내 유지 ("아직 데이터 없음 — 시드 추가 후 수집 실행, 점수는 2일차부터") + **CTA 버튼 2개(시드 추가/지금 수집 실행, v3)**
- **오류·빈 상태·로딩 (v3 명시)**: 첫 로드 스켈레톤 테이블, API 오류(404/500/네트워크) 시 "데이터를 불러오지 못했습니다" + [다시 시도], 상세 모달 404/네트워크 오류 패널, 온보딩 문구는 "전체 데이터 0건"일 때만

## 5. 스케줄러 (v2 개정)

- GitHub Actions cron `17 22 * * *` (= **매일 07:17 KST**. 정각은 혼잡으로 지연 잦음 → 오프셋)
- 워크플로우 필수 요소: `concurrency` 그룹(중복 실행 방지) · `timeout-minutes: 60`(행 방지 — 무료 분량 보호) · **keep-alive 스텝**(마지막 커밋 50일 경과 시 빈 커밋 푸시 → 60일 비활성화 방지, `contents: write` 권한)
- 실패 알림: 스냅샷이 0건이고 오류가 있으면 `collect.py`가 exit 1 → GitHub 기본 실패 메일 발송. **자동완성 차단(blocked)도 스냅샷 성공 여부와 무관하게 exit 1** (v3 정정 — v2는 스냅샷이 있으면 차단이 exit 0으로 조용히 통과). (선택) healthchecks.io 무료 핑을 마지막 스텝에 추가하면 "실행 자체가 안 됨"도 감지
- 대시보드 /status에 마지막 성공 수집 경과 표시 (2일 초과 시 경고색)
- **리스크**: GH 러너(데이터센터 IP)에서 자동완성 차단 가능 → 최초 실행 검증. 차단 시 cron-job.org(무료)가 Vercel `/collect`를 **POST + Authorization 헤더 + body `{"trigger":"schedule"}`**로 호출하는 대안 (v1 문서의 "GET 호출"은 오기 — 엔드포인트는 POST. **v2의 manual-only 호출은 발굴·수요·은퇴·보존이 누락되어 스케줄러를 대체하지 못했으므로 v3에서 trigger=schedule로 전 구간 대체**, 실행 예산은 Vercel 한도 내 45초 — 잔여 키워드는 다음 실행이 오래된 스냅샷부터 순환 처리)

## 6. 에러처리 전략 (v2 확장)

| 상황 | 대응 |
|---|---|
| 네이버 API 오류 (SE01~SE99, 403) | 해당 키워드 스킵 + 로그, 전체 중단 없음 |
| 자동완성 요청 실패 | 지수 백오프 3회 → 연속 5회 실패 또는 성공 0회면 크롤 중단 + `blocked` 로그 + **exit 1** |
| 자동완성 응답 포맷 변화 | 방어적 파싱(빈 결과) + config로 엔드포인트 교체 대응 |
| blog/shop 부분 실패 | 상업성만 NULL, 기회 점수는 정상 계산 |
| 데이터랩 실패/쿼터 소진 | **네트워크·타임아웃·JSON 오류를 DatalabError로 정규화 후** 수요 단계만 중단, 나머지 정상 (v3) |
| DB 커넥션 사망(서버) | 1회 재연결 후 재시도 — **수집 배치도 동일 (v3)** |
| Supabase 일시정지 | 수동 복구 필요 — /status 경고 + 실패 메일로 조기 인지 (§5) |
| 중복 실행 | **부분 유니크 인덱스로 원자 취득하는 DB 잠금(60분 stale 회수)** + Actions concurrency + 동일 날짜 스냅샷 스킵(멱등) (v3) |
| 수동 수집 Vercel 60초 초과 | 시간 예산 45초가 **발굴·개별 호출까지 전 구간 적용** + `partial` 응답 (§4.9) |
| 전체 수집 실패 | exit 1 → GitHub 실패 메일 |
| 네이버 정책/UI 변경 | 엔드포인트·블랙리스트 config 분리, 최소 수정 대응 |

## 7. 보안 (v2 강화)

- **쓰기 API 인증을 v1 필수로 승격**: `DASHBOARD_TOKEN` 설정 시 `/collect`, `/seeds` 쓰기, `/keywords` PATCH는 `Authorization: Bearer` 요구. 공개 URL에서 무인증 쓰기는 네이버 쿼터 소진·데이터 오염 어뷰징 벡터 (조회는 v1에서 공개 허용 — 전면 인증은 v1.1)
- **fail-closed (v3 정정)**: `ENV=production`에서 `DASHBOARD_TOKEN`이 미설정이면 **서버 기동을 거부**한다. 토큰 누락을 설정 실수로 방치하면 무인증 쓰기 API가 공개 상태로 열리므로, 정책은 "설정 시 인증"이 아니라 "프로덕션에서는 항상 인증"이다. 로컬 개발(ENV 미설정/development)만 인증 생략 허용
- 시크릿: 네이버 키·DATABASE_URL·토큰 → GitHub Secrets + Vercel Env. 레포 커밋 금지, 개발은 `.env`(gitignore)
- XSS: 대시보드에서 외부 유래 문자열 이스케이프 (§4.10)
- 참고 리스크: 자동완성은 비공식 엔드포인트로 **약관상 회색지대** — 저빈도 유지(요청 상한·간격), 차단 시 즉시 중단 설계로 노출 최소화. 수집 중단이 블로그 계정 제재로 이어지는 경로는 없음(읽기 전용)이나 인지하고 사용

## 8. 용량·쿼터 산정 (v2 신설 — 정상상태 활성 1,000개 기준)

## 9. 테스트 전략 (v2 개정)

- 전 모듈 단위 테스트 (네트워크 비의존 mock). **날짜는 하드코딩 금지** — 기준일을 인자로 주입하거나 상대 날짜로 생성 (v1은 하드코딩으로 시한폭탄 테스트 존재)
- 점수 공식: 경계값을 **공식으로 직접 검산한 기대값**으로 작성 (v1 계획은 잘못된 기대값 4건이 있었음)
- 수명주기: 은퇴 조건(**점수 NULL 보호 포함, v3**)·보존 정리·잠금(**원자 취득**, v3)·멱등(같은 날 스킵)·시간 예산 partial·**날짜 공백 시 성장률 NULL**(v3)
- 정제: 과차단 방지 케이스(성인병/전세대출/홍삼) + **필터 사유 반환 검증**(v3)
- API: 페이징·필터·인증(401)·PATCH·수동 수집 파라미터 전달·**정렬 방향·유망 프리셋·trigger=schedule·프로덕션 토큰 미설정 기동 거부**(v3)
- 통합: SQLite로 2일치 누적 → 점수 사전계산 검증
- **PostgreSQL 통합 테스트 (v3 신설)**: 로컬/CI Postgres(`DATABASE_URL` 설정 시)로 스키마 멱등 init·인덱스 존재·쿼리 동등성·**잠금 경합(동시 start_run — 원자성)**·**재연결(풀러 재시작 시뮬레이션)**·트랜잭션 경계를 검증. 배포 후에만 PG 다이얙트를 확인하던 v2 관행 제거
- **브라우저 E2E (v3 신설)**: 대시보드 렌더·빈 상태 CTA·오류 재시도·정렬 토글/aria-sort·스켈레톤·수동 수집 피드백 (Playwright, 선택 설치)
- 수동 확인: 자동완성 **실측 포맷 검증(구현 직후)**, GH Actions 실행, Vercel 배포, 데이터랩 응답, **배치 시간 실측(§8 표 갱신용, v3)**
